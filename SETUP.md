# Ю Кофе — настройка с нуля

Приложение хранит график в **Supabase**, а раз в сутки само складывает копию
данных в этот же репозиторий (папка `backups/`). Так данные лежат в двух
независимых местах и не пропадают вместе с одним аккаунтом.

Пройти шаги 1–5 нужно один раз, минут за двадцать.

---

## 1. Завести проект Supabase

1. Зарегистрироваться на [supabase.com](https://supabase.com) — **на почту, к которой
   точно есть доступ, и не на Google-аккаунт**, если он может быть заблокирован.
2. Create new project. Регион — Frankfurt (ближайший). План Free.
3. Пароль базы, который он попросит, сохранить в менеджер паролей: он нужен
   только для прямого доступа к Postgres, в приложении не используется.

## 2. Создать таблицы

Открыть **SQL Editor** → New query → вставить целиком содержимое
[`supabase/schema.sql`](supabase/schema.sql) → Run.

Скрипт создаёт четыре таблицы, включает realtime, настраивает права и заводит
четверых сотрудников по умолчанию. Запускать повторно безопасно.

## 3. Завести две учётки

**Authentication → Users → Add user → Create new user** (галочку
«Auto Confirm User» включить, иначе вход потребует подтверждения почты):

| Email                  | Пароль                | Кто это                                  |
|------------------------|-----------------------|------------------------------------------|
| `admin@u-coffee.app`   | PIN управляющего      | правит график, сотрудников, качает бэкап |
| `barista@u-coffee.app` | общий PIN для баристов| отмечает пожелания                       |

Почты ненастоящие и подтверждать их не надо — это просто логины. PIN лучше
делать из 6 цифр; в самом приложении паролей нет, проверяет их сервер.

Права разделены в `schema.sql`: график может писать только `admin@u-coffee.app`,
пожелания — любой вошедший, а без входа график только читается.

## 4. Прописать ключи в приложение

**Project Settings → API**, оттуда взять два значения и вписать в
[`lib/supabase_config.dart`](lib/supabase_config.dart):

- `url` — Project URL, вида `https://xxxxxxxx.supabase.co`
- `publishableKey` — публичный ключ (`sb_publishable_...`, в старых проектах `anon`)

Оба значения публичные по замыслу: их видно в браузере у любого пользователя,
а защищают данные правила доступа из `schema.sql`. **Ключ `service_role` сюда
класть нельзя ни при каких обстоятельствах** — он обходит все правила.

После правки — `git commit` и `git push`, GitHub сам пересоберёт и выложит сайт.

## 5. Включить автоматический бэкап

**Settings → Secrets and variables → Actions → New repository secret**, добавить два:

| Имя                          | Значение                          |
|------------------------------|-----------------------------------|
| `SUPABASE_URL`               | тот же Project URL                |
| `SUPABASE_PUBLISHABLE_KEY`   | тот же публичный ключ             |

Проверить сразу: вкладка **Actions → Бэкап графика → Run workflow**. Через минуту
в репозитории должна появиться папка `backups/` с четырьмя JSON-файлами.
Дальше он ходит сам каждую ночь и коммитит только когда данные изменились.

⚠️ GitHub отключает расписание в репозиториях, где 60 дней не было активности.
Ежедневные коммиты бэкапа сами по себе считаются активностью, так что пока данные
меняются — всё работает. Если график не трогали два месяца, расписание надо
включить обратно кнопкой в Actions.

---

## Если данные придётся восстанавливать

```bash
SUPABASE_URL=https://xxx.supabase.co SUPABASE_SERVICE_KEY=<service_role> ./supabase/restore.sh
```

`service_role`-ключ берётся в Project Settings → API на время восстановления и
нигде не сохраняется. Скрипт заливает `backups/*.json` обратно, существующие
записи обновляются, а не дублируются.

Ещё есть кнопка со стрелкой вниз в шапке приложения (видна управляющему) —
скачивает текущий график одним JSON-файлом на устройство.

## Что делать, если база недоступна

Приложение держит последний загруженный график в памяти браузера и показывает
его вместе с красной плашкой «Нет связи с базой». То есть баристы видят
расписание, даже когда сервер лежит; не сохраняются только изменения.
